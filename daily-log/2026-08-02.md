# 2026-08-02 — Day 2: Writing Systemd Services & journalctl Debugging

Today I practiced writing proper systemd services instead of just running scripts in tmux or screen sessions. If you want things to run reliably in production, systemd is non-negotiable.

---

## What I worked on today
- Wrote a custom unit file `/etc/systemd/system/node-monitor.service` for a small Python telemetry script.
- Configured auto-restart policies (`Restart=always`, `RestartSec=5s`) so it recovers automatically if it crashes.
- Created a dedicated service user (`monitor`) with `/usr/sbin/nologin` so the daemon doesn't run as root.
- Explored `journalctl` flags to view logs in real time.

---

## Commands I ran
```bash
# Reload systemd to pick up the new unit file
sudo systemctl daemon-reload
sudo systemctl enable --now node-monitor.service

# Check status and stream logs
sudo systemctl status node-monitor.service
journalctl -u node-monitor.service -f -n 50
```

---

## The problem I ran into & how I solved it
* **What I was trying to do:** Starting the newly created service
* **The error:** `The service kept crash-looping with status `(code=exited, status=2)`.`
* **What actually caused it:** I referenced `EnvironmentFile=/etc/default/node-monitor`, but inside that file I forgot to quote an API key that contained special characters (`#` and `@`), which messed up systemd's parsing.
* **How I fixed it:** Wrapped all environment values in double quotes, ran `systemd-analyze verify node-monitor.service` to test the syntax, and restarted.
* **Takeaway / lesson learned:** `systemd-analyze verify <service>` is awesome. It catches syntax and path errors immediately before you even start the service.

---

## Key takeaways from today
- Never run background services as root unless they genuinely need raw hardware access.
- `journalctl -xeu <service>` gives you the exact surrounding context when a service crashes.
