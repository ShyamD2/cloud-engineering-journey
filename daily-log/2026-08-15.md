# 2026-08-15 — Day 15: Security Groups vs NACLs: The Stateless Return Traffic Trap

Today I ran an experiment specifically comparing Security Groups and Network ACLs. I finally understand why ephemeral port rules are so critical on NACLs.

---

## What I worked on today
- Set up a Security Group allowing inbound HTTP (80) and HTTPS (443).
- Set up a custom Network ACL with numbered rules.
- Tested why outbound return traffic dropped when ephemeral ports weren't explicitly permitted.

---

## Commands I ran
```bash
aws ec2 create-security-group --group-name web-sg --description 'Web server SG' --vpc-id vpc-01234567
aws ec2 authorize-security-group-ingress --group-id sg-01234567 --protocol tcp --port 443 --cidr 0.0.0.0/0
aws ec2 create-network-acl-entry --network-acl-id acl-01234567 --rule-number 100 --protocol tcp --rule-action allow --ingress --cidr-block 0.0.0.0/0 --port-range From=443,To=443
```

---

## The problem I ran into & how I solved it
* **What I was trying to do:** Sending a curl request to the web server
* **The error:** ``curl: (28) Failed to connect to <ip>: Connection timed out`.`
* **What actually caused it:** Security Groups are stateful (they automatically allow return responses), but NACLs are stateless. My inbound NACL allowed port 443, but the outbound NACL blocked the server's response packets back to the client's ephemeral ports.
* **How I fixed it:** Added an outbound rule to the NACL allowing TCP traffic to `0.0.0.0/0` on ports `1024-65535`.
* **Takeaway / lesson learned:** If you touch custom NACLs, you MUST allow outbound ephemeral ports (1024-65535). Otherwise, incoming connections can never respond.

---

## Key takeaways from today
- Security Groups operate at the instance/ENI level; NACLs operate at the subnet boundary.
- Security Groups evaluate all rules together; NACLs evaluate in numerical order from lowest to highest.
