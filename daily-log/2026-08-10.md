# 2026-08-10 — Day 10: AWS IAM Policies, Evaluation Logic & Boundaries

Dug deep into IAM policies today. IAM can look straightforward until you hit a weird denial. Understanding how AWS evaluates policies internally makes debugging permissions way easier.

---

## What I worked on today
- Wrote a custom IAM JSON policy that forces all S3 operations to use HTTPS/TLS 1.2 (`aws:SecureTransport: true`).
- Tested how IAM Permissions Boundaries act as a maximum ceiling on permissions.
- Used the AWS IAM Policy Simulator to test access before applying policies.

---

## Commands I ran
```bash
aws iam create-policy --policy-name EnforceTlsS3Access --policy-document file://s3-tls-policy.json
aws iam simulate-principal-policy --policy-source-arn arn:aws:iam::197550036081:user/dev-cli-user --action-names s3:GetObject
```

---

## The problem I ran into & how I solved it
* **What I was trying to do:** Uploading an object to S3 with a user that had full S3 access attached
* **The error:** `Got `AccessDenied` on `PutObject` despite having `AmazonS3FullAccess`.`
* **What actually caused it:** The IAM user had a Permissions Boundary attached that didn't include `s3:PutObject`.
* **How I fixed it:** Updated the Permissions Boundary to permit the required S3 actions.
* **Takeaway / lesson learned:** An IAM policy cannot grant more permissions than what the attached Permissions Boundary allows; effective access is the intersection of both.

---

## Key takeaways from today
- Policy evaluation hierarchy: Explicit Deny always wins -> Needs Explicit Allow -> Defaults to Implicit Deny.
- Condition keys like `aws:SourceIp` and `aws:SecureTransport` are great for Zero-Trust enforcement.
