# 2026-08-18 — Day 18: EC2 Launch Templates & IMDSv2 Hardening

Standardized my EC2 deployments today using versioned Launch Templates instead of clicking around in the console or using legacy Launch Configurations.

---

## What I worked on today
- Wrote a clean cloud-init user-data script to install Docker, NGINX, and basic monitoring.
- Created an EC2 Launch Template with gp3 root storage.
- Enforced IMDSv2 (`HttpTokens=required`) to protect against SSRF attacks.

---

## Commands I ran
```bash
aws ec2 create-launch-template --launch-template-name prod-web-template --launch-template-data file://lt-config.json
TOKEN=$(curl -s -X PUT 'http://169.254.169.254/latest/api/token' -H 'X-aws-ec2-metadata-token-ttl-seconds: 21600')
curl -s -H "X-aws-ec2-metadata-token: $TOKEN" http://169.254.169.254/latest/meta-data/instance-id
```

---

## The problem I ran into & how I solved it
* **What I was trying to do:** Checking if user-data started NGINX on boot
* **The error:** `Instance launched, but NGINX wasn't running and web page returned connection refused.`
* **What actually caused it:** My user-data script failed on a typo in the config copy command.
* **How I fixed it:** SSM'd into the box, read `/var/log/cloud-init-output.log` to see the exact error line, fixed the template, and launched version 2.
* **Takeaway / lesson learned:** Always check `/var/log/cloud-init-output.log` when an EC2 user-data bootstrap script fails.

---

## Key takeaways from today
- IMDSv2 requires a session token obtained via an HTTP PUT request; plain GET requests are blocked.
- Launch Templates allow easy versioning, inheritance, and mixed instance policies.
