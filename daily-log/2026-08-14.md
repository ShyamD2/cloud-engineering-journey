# 2026-08-14 — Day 14: NAT Gateway Setup & Private Outbound Access

Configured a managed NAT Gateway today so instances sitting in private subnets can run `apt update` or pull container images without being exposed to incoming internet traffic.

---

## What I worked on today
- Allocated an Elastic IP for the NAT Gateway.
- Deployed a NAT Gateway inside the public subnet.
- Updated the private subnet route table to direct outbound traffic (`0.0.0.0/0`) through the NAT Gateway.

---

## Commands I ran
```bash
aws ec2 allocate-address --domain vpc
aws ec2 create-nat-gateway --subnet-id subnet-public-1a --allocation-id eipalloc-01234567
aws ec2 create-route --route-table-id rtb-private-1a --destination-cidr-block 0.0.0.0/0 --nat-gateway-id nat-01234567
```

---

## The problem I ran into & how I solved it
* **What I was trying to do:** Creating the NAT Gateway
* **The error:** `The NAT Gateway immediately failed and went into `failed` status.`
* **What actually caused it:** I accidentally selected a private subnet when provisioning it. A NAT Gateway must live in a public subnet with a route to an IGW.
* **How I fixed it:** Re-provisioned it inside `subnet-public-1a` (which has the IGW route) and pointed the private route table to it.
* **Takeaway / lesson learned:** NAT Gateways must reside in a public subnet to translate private traffic to its Elastic IP, but the instances using it reside in private subnets.

---

## Key takeaways from today
- NAT Gateways cost ~$32.40/month each plus data transfer ($0.045/GB); delete test NAT Gateways as soon as the lab is done!
- In production, deploy one NAT Gateway per AZ for high availability.
