# 2026-08-06 — Day 6: Linux Storage: LVM & Live Filesystem Expansion

Today I practiced Logical Volume Manager (LVM) operations. Running out of disk space on a database or app server is a rite of passage, and knowing how to add space on the fly without unmounting is crucial.

---

## What I worked on today
- Initialized physical volumes on a newly attached virtual disk (`/dev/sdb`).
- Created volume group `vg_data` and allocated a 20GB logical volume `lv_app`.
- Formatted it with XFS, mounted it, and grew the volume to 30GB while actively writing data to it.

---

## Commands I ran
```bash
sudo pvcreate /dev/sdb1
sudo vgcreate vg_data /dev/sdb1
sudo lvcreate -L 20G -n lv_app vg_data
sudo mkfs.xfs /dev/vg_data/lv_app
sudo lvextend -L +10G /dev/vg_data/lv_app
sudo xfs_growfs /var/app/data
```

---

## The problem I ran into & how I solved it
* **What I was trying to do:** Expanding the filesystem using resize2fs
* **The error:** ``resize2fs: Bad magic number in super-block while trying to open /dev/vg_data/lv_app`.`
* **What actually caused it:** I ran `resize2fs` (which is for ext4) on an XFS filesystem.
* **How I fixed it:** Switched to `xfs_growfs /var/app/data` (note that XFS takes the mount point, whereas resize2fs takes the device path).
* **Takeaway / lesson learned:** XFS can only grow (it cannot be shrunk) and requires `xfs_growfs <mountpoint>`. Ext4 uses `resize2fs <device>`.

---

## Key takeaways from today
- LVM abstracts raw storage disks so you can combine multiple disks into a single volume group.
- Always use filesystem UUIDs in `/etc/fstab` instead of device names like `/dev/sdb1`.
