# 2026-08-05 — Day 5: SSH Hardening & Bastion Host ProxyJump

Hardened SSH configurations today and set up clean multi-hop jump configs. Having to manually SSH into a jump box and then SSH from there into a private server is annoying; `ProxyJump` makes it seamless.

---

## What I worked on today
- Generated modern Ed25519 SSH keys (`ssh-keygen -t ed25519 -C 'shyam-dev'`).
- Hardened `/etc/ssh/sshd_config` by disabling password authentication, disabling root login, and setting max auth tries to 3.
- Configured my local `~/.ssh/config` file with `ProxyJump` for frictionless bastion access.

---

## Commands I ran
```bash
# Generate Ed25519 keypair
ssh-keygen -t ed25519 -f ~/.ssh/id_ed25519_infra -C 'infra-key'

# Add to ssh-agent
eval $(ssh-agent -s)
ssh-add ~/.ssh/id_ed25519_infra

# Connect directly through bastion in one shot
ssh -J bastion.lab.net internal-server-01
```

---

## The problem I ran into & how I solved it
* **What I was trying to do:** Connecting to an internal server through the jump box
* **The error:** `Got `Host key verification failed` when attempting to connect.`
* **What actually caused it:** The target VM had been re-imaged with a new host key, which clashed with the old fingerprint saved in my `known_hosts` file.
* **How I fixed it:** Verified the new fingerprint via the hypervisor console, cleaned out the old entry with `ssh-keygen -R 10.0.10.45`, and reconnected.
* **Takeaway / lesson learned:** `ProxyJump` establishes an end-to-end encrypted connection straight between your laptop and the private target server; the bastion never sees your private key or decrypted traffic.

---

## Key takeaways from today
- Ed25519 keys are faster, shorter, and more secure than legacy RSA 2048/4096.
- Avoid `ForwardAgent yes` on untrusted jump hosts; `ProxyJump` is significantly safer.
