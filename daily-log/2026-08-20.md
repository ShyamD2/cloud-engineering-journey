# 2026-08-20 — Day 20: Application Load Balancer & Health Check Tuning

Configured an internet-facing Application Load Balancer (ALB) across two public subnets today and set up path-based routing rules to direct traffic to different backend target groups.

---

## What I worked on today
- Deployed an ALB in public subnets across `ap-south-1a` and `ap-south-1b`.
- Created Target Groups for API services (port 8080) and frontend (port 80).
- Configured listener rules: `/api/*` routes to the API target group, everything else to frontend.

---

## Commands I ran
```bash
aws elbv2 create-load-balancer --name prod-alb --subnets subnet-pub-1 subnet-pub-2 --security-groups sg-alb
aws elbv2 create-target-group --name tg-api --protocol HTTP --port 8080 --vpc-id vpc-01234567 --health-check-path /api/health
aws elbv2 create-listener --load-balancer-arn arn:aws:... --protocol HTTP --port 80 --default-actions Type=forward,TargetGroupArn=arn:aws:...
```

---

## The problem I ran into & how I solved it
* **What I was trying to do:** Accessing the app through the ALB DNS name
* **The error:** `ALB returned `HTTP 502 Bad Gateway`.`
* **What actually caused it:** The Target Group health checks were failing because the backend EC2 security group didn't allow inbound traffic from the ALB's security group.
* **How I fixed it:** Updated backend instance Security Group to allow inbound port 8080 specifically from the ALB's Security Group ID (`sg-alb`).
* **Takeaway / lesson learned:** Always reference the ALB's Security Group ID in backend instance security groups instead of opening ports to wide IP ranges.

---

## Key takeaways from today
- ALBs operate at Layer 7, giving you path-based, host-based, and HTTP header routing capabilities.
- Unhealthy targets cause 502 Bad Gateway errors; check target group health status first.
