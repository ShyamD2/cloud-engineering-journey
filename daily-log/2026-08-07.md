# 2026-08-07 — Day 7: Defensive Bash Scripting & Automation

Refactored my automation scripts today. Quick one-line bash scripts are fine for personal use, but for production bootstrap, you need strict error handling so broken scripts fail fast instead of doing partial damage.

---

## What I worked on today
- Added `set -euo pipefail` to all my infrastructure scripts.
- Added cleanup exit traps (`trap cleanup EXIT SIGINT SIGTERM`) to automatically delete temporary files if a script errors or gets cancelled.
- Parsed command line flags properly using bash's builtin `getopts`.
- Ran `shellcheck` to catch subtle quoting and portability issues.

---

## Commands I ran
```bash
# Check script syntax without running it
bash -n bootstrap.sh

# Run static analysis
shellcheck bootstrap.sh

# Test with flags
./bootstrap.sh -e production -v
```

---

## The problem I ran into & how I solved it
* **What I was trying to do:** Testing error handling in a piped command
* **The error:** `A database query in `psql ... | grep ERROR` failed, but the script kept right on executing the next line!`
* **What actually caused it:** Standard `set -e` only checks the exit code of the last command in a pipeline (`grep`), which succeeded with exit 1 (no match) or 0.
* **How I fixed it:** Added `set -o pipefail`. Now if any command in the pipe fails, the entire pipeline returns that error code.
* **Takeaway / lesson learned:** `set -e` alone is not enough; you almost always want `set -euo pipefail` for scripts handling infrastructure.

---

## Key takeaways from today
- `set -e`: exit on error; `set -u`: treat unset variables as error; `set -o pipefail`: don't ignore errors in pipes.
- `shellcheck` is a lifesaver. It pointed out 3 unquoted variables that could have broken with spaces in paths.
