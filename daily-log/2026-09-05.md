# 2026-09-05 — Day 36: Terraform Workspaces & Multi-Environment Deployments

Experimented with Terraform Workspaces today to see how teams deploy development, staging, and production environments from the same codebase.

---

## What I worked on today
- Created workspaces: `terraform workspace new dev` and `staging`.
- Used `${terraform.workspace}` inside resource names and tags.
- Used ternary expressions to pick instance sizes based on active workspace.

---

## Commands I ran
```bash
terraform workspace list
terraform workspace select dev
terraform plan -var-file=environments/dev.tfvars
```

---

## The problem I ran into & how I solved it
* **What I was trying to do:** Switching workspaces and checking plan
* **The error:** `Plan in staging tried to delete dev resources.`
* **What actually caused it:** I had a hardcoded S3 backend key in my config, which overrode workspace state separation.
* **How I fixed it:** Removed the hardcoded key so Terraform's S3 backend automatically uses `env:/<workspace_name>/` prefixes.
* **Takeaway / lesson learned:** Workspaces automatically isolate state in S3 when configured properly.

---

## Key takeaways from today
- Workspaces are convenient for identical ephemeral environments.
- For large production vs dev setups with different architectures, separate directory layouts are often cleaner.
