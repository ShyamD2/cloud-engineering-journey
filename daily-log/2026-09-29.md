## The problem I ran into & how I solved it
* **What I was trying to do:** Run the 100-task empirical benchmark runner on GitHub Actions Windows Server runner.
* **The error:** The benchmark scored 86/100 on CI, causing the CI verification step to fail (<90% threshold).
* **What actually caused it:** On headless cloud runners: (1) `netsh wlan show interfaces` hung because the Windows Server runner lacks a Wi-Fi service/card; (2) `powershell Get-NetAdapter` took over 5 seconds under VM load; (3) Azure firewalls drop outgoing ICMP ping packets, timing out after 10 seconds. Three successive failures on `network.control` tripped the circuit breaker, which then fast-failed 6 subsequent network tasks.
* **How I fixed it:** Replaced PowerShell adapter discovery with `psutil.net_if_stats()` (<1ms, zero subprocess overhead), clamped ping to a 2-second timeout with reachability flags, and treated headless absence of Wi-Fi cards as valid ground-truth sensor telemetry rather than tool crashes.
* **Takeaway / lesson learned:** In cyber-physical automation, an agent must distinguish between *software execution failures* and *physical sensor absence*. A server without a Wi-Fi card reporting `connected: false` is a successful sensory observation, not a broken tool.

---

## Key takeaways from today
- **Zero-Subprocess Telemetry**: Spawning external shells (`powershell.exe`, `netsh.exe`) inside high-frequency agent loops introduces severe process startup latency and timeout fragility. Using native Python libraries (`psutil`, `ctypes`, `socket`) reduces latency from 5,000ms to <1ms.
- **Circuit Breaker Tuning**: Circuit breakers must only trip on genuine service exceptions and crashes, never on valid negative ground-truth observations.
