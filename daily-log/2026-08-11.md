# 2026-08-11 — Day 11: IAM Roles, Instance Profiles & STS AssumeRole

Today was about IAM Roles. Hardcoding access keys onto an EC2 server is a massive anti-pattern. IAM Instance Profiles are how you do things the right way.

---

## What I worked on today
- Created an IAM Role `EC2-S3-ReadRole` with an EC2 service trust policy (`ec2.amazonaws.com`).
- Created an Instance Profile and attached it to the role.
- Tested assuming a role programmatically using `aws sts assume-role`.

---

## Commands I ran
```bash
aws iam create-role --role-name EC2-S3-ReadRole --assume-role-policy-document file://trust-policy.json
aws iam create-instance-profile --instance-profile-name EC2-S3-Profile
aws iam add-role-to-instance-profile --instance-profile-name EC2-S3-Profile --role-name EC2-S3-ReadRole
aws sts assume-role --role-arn arn:aws:iam::197550036081:role/EC2-S3-ReadRole --role-session-name test-session
```

---

## The problem I ran into & how I solved it
* **What I was trying to do:** Assuming a role from another account
* **The error:** ``An error occurred (AccessDenied) when calling the AssumeRole operation`.`
* **What actually caused it:** The target role's trust policy was missing the calling user's ARN in its `Principal` block.
* **How I fixed it:** Added the caller's ARN to the `Principal` block of the target role's trust relationship.
* **Takeaway / lesson learned:** A role needs two policies: a Trust Policy (who can assume it) and a Permissions Policy (what it can do once assumed).

---

## Key takeaways from today
- Instance Profiles automatically handle rotating temporary credentials behind the scenes via the metadata service.
- Never commit `.aws/credentials` or access keys to GitHub.
