# 2026-08-19 — Day 19: EBS Volumes: Live Resizing Without Downtime

Practiced modifying EBS volumes on live running instances today. It's awesome that AWS lets you grow disk space and IOPS on the fly without unmounting or rebooting.

---

## What I worked on today
- Modified an attached 20GB gp3 EBS volume to 35GB and 4,000 IOPS via AWS CLI.
- Monitored the volume state as it transitioned to `optimizing`.
- Expanded the partition and XFS filesystem on the live Linux instance.

---

## Commands I ran
```bash
aws ec2 modify-volume --volume-id vol-01234567 --size 35 --iops 4000
lsblk
sudo growpart /dev/xvdf 1
sudo xfs_growfs -d /mnt/data
```

---

## The problem I ran into & how I solved it
* **What I was trying to do:** Running growpart right after AWS CLI command
* **The error:** ``NOCHANGE: partition 1 is size 41943040. it cannot be grown`.`
* **What actually caused it:** I ran `growpart` too quickly before the AWS backend finished modifying the volume size and the kernel noticed the change.
* **How I fixed it:** Waited about 30 seconds for the kernel to recognize the new geometry (`dmesg | grep xvdf`) and ran `growpart` again.
* **Takeaway / lesson learned:** Wait for the EBS volume status to transition from `modifying` to `optimizing` before running partition resizing tools in the OS.

---

## Key takeaways from today
- You can grow EBS volumes online, but you can NEVER shrink an EBS volume directly.
- gp3 lets you scale IOPS and throughput independently without buying unneeded disk space.
