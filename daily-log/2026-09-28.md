## The problem I ran into & how I solved it
* **What I was trying to do:** Search the entire Linux root filesystem (`find /`) as an unprivileged user for a file with specific user and group ownership.
* **The error:** The terminal flooded with hundreds of `find: ‘/etc/ssl/private’: Permission denied` messages, completely obscuring the single valid matching file.
* **What actually caused it:** Standard search tools emit directory traversal permission failures to stderr (file descriptor 2) while standard matches go to stdout (file descriptor 1).
* **How I fixed it:** Appended `2>/dev/null` to the search command (`find / -user bandit7 -group bandit6 -size 33c 2>/dev/null`). This redirects all permission error messages to the Linux bit-bucket while printing the clean matching path on stdout.
* **Takeaway / lesson learned:** In cloud automation and CI/CD pipelines, redirecting or capturing stderr selectively is critical to prevent noisy diagnostic logs from hiding legitimate matching signals.

## Key takeaways from today
- **Directory Traversal Bit**: The execute bit (`x`) on a directory controls entry (`cd`) and access to files within it. Without `x`, a user cannot open a `644` file inside, even if they have read permissions on the file itself.
- **Strict SSH Key Permissions**: OpenSSH enforces strict DAC checks. A private key readable by anyone other than the owner (`chmod 644 id_rsa`) triggers client termination. `chmod 600` is mandatory for cloud secrets.
