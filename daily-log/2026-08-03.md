# 2026-08-03 — Day 3: Linux Sockets & Network Diagnostics

Focused on Linux networking diagnostics today. In older tutorials, everyone used `netstat`, but `ss` (socket statistics) is way faster because it talks directly to the Linux kernel via Netlink.

---

## What I worked on today
- Replaced my old `netstat` muscle memory with `ss -tulpn` (TCP, UDP, Listening, Process info, Numeric ports).
- Inspected socket lifecycle states like `ESTABLISHED`, `TIME_WAIT`, and `CLOSE_WAIT`.
- Checked local routing tables using `ip route show` and investigated default gateways.

---

## Commands I ran
```bash
# See all listening TCP/UDP ports with their PID and process name
ss -tulpn

# Quick summary of total open sockets
ss -s

# Inspect local route table
ip route show
```

---

## The problem I ran into & how I solved it
* **What I was trying to do:** Starting NGINX on port 8080
* **The error:** `NGINX threw `bind() to 0.0.0.0:8080 failed (98: Address already in use)`.`
* **What actually caused it:** A test Python web server I ran yesterday was still running in the background holding onto port 8080.
* **How I fixed it:** Ran `ss -tulpn | grep 8080` to find the offending PID (4192), verified what it was, and terminated it with `kill -15 4192`.
* **Takeaway / lesson learned:** When a port is in use, `ss -tulpn | grep <port>` immediately shows you the PID so you don't have to guess.

---

## Key takeaways from today
- `ss` queries kernel socket data directly and is much faster on high-connection servers than `netstat`.
- `TIME_WAIT` sockets are normal after a connection closes; the OS keeps them briefly to catch delayed packets.
