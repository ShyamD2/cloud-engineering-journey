# 2026-08-12 — Day 12: AWS VPC Design & Subnet Math

Designed a custom VPC from scratch today. Default VPCs are okay for quick throwaway tests, but in production, you want clear subnet tiers across multiple Availability Zones.

---

## What I worked on today
- Planned a VPC CIDR `10.0.0.0/16` (65,536 IPs).
- Carved out public subnets (`10.0.1.0/24`, `10.0.2.0/24`) for ALBs and NAT Gateways.
- Carved out private app subnets (`10.0.10.0/24`, `10.0.11.0/24`) and isolated DB subnets (`10.0.20.0/24`, `10.0.21.0/24`).

---

## Commands I ran
```bash
aws ec2 create-vpc --cidr-block 10.0.0.0/16 --tag-specifications 'ResourceType=vpc,Tags=[{Key=Name,Value=prod-vpc}]'
aws ec2 create-subnet --vpc-id vpc-01234567 --cidr-block 10.0.1.0/24 --availability-zone ap-south-1a
aws ec2 create-subnet --vpc-id vpc-01234567 --cidr-block 10.0.10.0/24 --availability-zone ap-south-1a
```

---

## The problem I ran into & how I solved it
* **What I was trying to do:** Creating a small `/28` subnet for database testing
* **The error:** `AWS Console showed only 11 available IPs instead of the expected 16.`
* **What actually caused it:** AWS always reserves the first 4 IPs and the last IP in every subnet for network, router, DNS, future use, and broadcast.
* **How I fixed it:** Resized my database subnets to `/24` (251 usable IPs) so we don't run into IP exhaustion when spinning up replicas.
* **Takeaway / lesson learned:** Always subtract 5 from any subnet size calculation when designing AWS networks (`2^(32-prefix) - 5`).

---

## Key takeaways from today
- Once a VPC is created, you can't resize existing subnets; you have to plan CIDRs carefully upfront.
- Database subnets should never have an internet route or public IPs.
