# 2026-08-24 — Day 24: Amazon RDS PostgreSQL: Multi-AZ Failover Testing

Provisioned an Amazon RDS PostgreSQL database today and actually tested a forced failover to see how application clients handle primary database reboots.

---

## What I worked on today
- Created a DB Subnet Group spanning isolated private database subnets.
- Provisioned a PostgreSQL 15 instance with Multi-AZ enabled and 7-day automated backups.
- Triggered a manual reboot with failover via AWS CLI and watched the DNS CNAME update.

---

## Commands I ran
```bash
aws rds create-db-subnet-group --db-subnet-group-name rds-priv-subnets --db-subnet-group-description 'RDS subnets' --subnet-ids subnet-db-1 subnet-db-2
aws rds create-db-instance --db-instance-identifier prod-db --db-instance-class db.t4g.medium --engine postgres --allocated-storage 20 --multi-az --db-subnet-group-name rds-priv-subnets
aws rds reboot-db-instance --db-instance-identifier prod-db --force-failover
```

---

## The problem I ran into & how I solved it
* **What I was trying to do:** Application reconnecting after failover
* **The error:** `App kept failing with connection timeouts for almost 4 minutes after the reboot finished.`
* **What actually caused it:** The backend application cached the old IP address of the database endpoint because the runtime had DNS caching set to indefinite.
* **How I fixed it:** Configured DNS cache TTL in the application environment to 5 seconds (`networkaddress.cache.ttl=5`).
* **Takeaway / lesson learned:** In RDS Multi-AZ, the DNS hostname stays identical while AWS updates the CNAME to point to the standby replica; client apps must respect low DNS TTLs.

---

## Key takeaways from today
- RDS Multi-AZ is synchronous replication for high availability; Read Replicas are asynchronous for scaling read queries.
- Never put database instances in public subnets.
