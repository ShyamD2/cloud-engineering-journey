## The problem I ran into & how I solved it
* **What I was trying to do:** Ensuring the acoustic wake-word engine responded immediately with the authentic chime (`jarvis_on.mp3`) when speaking "Hey Jarvis" and executed commands without manual app launches.
* **The error:** Speaking "Hey Jarvis" did not trigger the wake chime, and J.A.R.V.I.S. appeared unresponsive in the background.
* **What actually caused it:** Three distinct issues:
  1. No background Python listener process was active initially prior to service configuration.
  2. Windows default audio input had bound to Device 1 (`Microphone (DroidCam Virtual Audio)`), which produces 0 dB silence when the mobile phone app is disconnected, rather than physical Device 2 (`Microphone Array (Intel® Smart Sound Technology)`).
  3. The internal command parser had a loop defect where regex `^\s*jarvis` failed to match `"hey jarvis"` because of the leading `"hey"`, causing `"hey jarvis"` to be treated as an unparsed command sent directly to the LLM rather than triggering the activation chime.
* **How I fixed it:**
  1. Updated audio device filtering to explicitly bypass virtual/loopback drivers and lock to the physical Intel array with dynamic energy threshold clamping (150–550 RMS).
  2. Patched prefix extraction in `wake_word_daemon.py` using comprehensive regex patterns (`r"^(?:hey|hi|hello|ok)?\s*jarvis[\s,:]*"`) so that speaking "Hey Jarvis" immediately plays the `wake_chime` and listens for the subsequent instruction.
  3. Configured persistent background execution via `pythonw.exe` and registered it into both `%APPDATA%\...\Startup` and the Windows Registry Run key.
* **Takeaway / lesson learned:** In voice-first ambient AI architectures, input hardware auto-selection must explicitly differentiate physical hardware from virtual software drivers, and acoustic wake-word parsing must be decoupled from conversational LLM dispatch to guarantee sub-second feedback.
