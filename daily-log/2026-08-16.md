# 2026-08-16 — Day 16: VPC Peering & Routing Across VPCs

Connected two different VPCs today (`10.100.0.0/16` and `10.200.0.0/16`) using AWS VPC Peering. Simple concept, but route tables can trip you up easily.

---

## What I worked on today
- Initiated and accepted a VPC Peering connection (`pcx-xxxx`).
- Updated route tables in both VPCs so traffic knows how to route across the peering link.
- Tested cross-VPC ping and private API communication.

---

## Commands I ran
```bash
aws ec2 create-vpc-peering-connection --vpc-id vpc-prod --peer-vpc-id vpc-shared
aws ec2 accept-vpc-peering-connection --vpc-peering-connection-id pcx-01234567
aws ec2 create-route --route-table-id rtb-prod --destination-cidr-block 10.200.0.0/16 --vpc-peering-connection-id pcx-01234567
```

---

## The problem I ran into & how I solved it
* **What I was trying to do:** Pinging between instances in the two peered VPCs
* **The error:** `Packets left VPC-A, but never returned (100% packet loss).`
* **What actually caused it:** Asymmetric routing: I added the route in VPC-A's route table pointing to VPC-B, but forgot to add the return route in VPC-B pointing back to VPC-A.
* **How I fixed it:** Added `10.100.0.0/16 -> pcx-01234567` into VPC-B's route table.
* **Takeaway / lesson learned:** VPC Peering is never automatic; you must update route tables on BOTH sides of the peering connection.

---

## Key takeaways from today
- VPC Peering is non-transitive. A <-> B and B <-> C does NOT let A talk to C.
- VPC CIDR ranges cannot overlap if you want to peer them.
