## The problem I ran into & how I solved it
* **What I was trying to do:** Ensure sensory ground-truth verification cannot be spoofed by timing delays or fast-exiting GUI windows.
* **The error:** When launching and closing ephemeral processes (like Notepad or calculator during automated benchmark runs), `psutil.process_iter()` occasionally picked up lingering zombie handles, reporting the process as still alive.
* **What actually caused it:** Windows OS kernel process table cleanup has an asynchronous reap latency (10–40ms) before the PID handle is fully released.
* **How I fixed it:** Implemented dual-channel verification in `VerificationAuthority`: combining PID termination checks with Windows Win32 UIAutomation element enumeration (`IUIAutomationElement.CurrentProcessId`). If neither the PID exists nor any top-level HWND responds to `WM_NULL`, reality confirms the process is truly dead.
* **Takeaway / lesson learned:** Never rely on a single telemetry source in mission-critical automation. Dual-channel verification with independent kernel primitives guarantees 0% false success.
