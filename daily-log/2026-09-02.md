# 2026-09-02 — Day 33: Terraform Remote State & DynamoDB Locking

Set up a production-grade remote backend for Terraform today. Keeping state files on your local machine is dangerous—if your laptop dies or two people apply at the same time, state gets corrupted.

---

## What I worked on today
- Created an S3 bucket for state with Versioning and KMS encryption enabled.
- Created a DynamoDB table `terraform-state-lock` with primary key `LockID`.
- Migrated my local state to S3 using `terraform init -migrate-state`.

---

## Commands I ran
```bash
terraform init -migrate-state
terraform plan
aws dynamodb scan --table-name terraform-state-lock
```

---

## The problem I ran into & how I solved it
* **What I was trying to do:** Running terraform apply after my terminal disconnected
* **The error:** ``Error: Error acquiring the state lock: ConditionalCheckFailedException`.`
* **What actually caused it:** Because the terminal closed mid-run, the DynamoDB lock wasn't released.
* **How I fixed it:** Grabbed the LockID from the error message and ran `terraform force-unlock <LockID>` after confirming no other process was running.
* **Takeaway / lesson learned:** State locking prevents disastrous concurrent applies; `force-unlock` is your tool to clear orphan locks after terminal crashes.

---

## Key takeaways from today
- Terraform state files can contain plaintext secrets; encrypt your S3 backend bucket and restrict IAM access.
- Enable S3 versioning on your state bucket so you can roll back if state gets corrupted.
