# 2026-09-07 — Day 38: Docker Multi-Stage Builds & Image Size Optimization

Worked on container optimization today. My first attempt at containerizing a Python app produced a ridiculous 1.25 GB image. Multi-stage builds fixed that completely.

---

## What I worked on today
- Compared single-stage vs multi-stage Dockerfiles.
- Set up `.dockerignore` to exclude local virtual environments and `.git` folders.
- Separated compilation tools (gcc, build-essential) into a builder stage and shipped only runtime wheels in the final stage.

---

## Commands I ran
```bash
docker build -t api-service:single -f Dockerfile.single .
docker build -t api-service:multi -f Dockerfile.multi .
docker images --format 'table {{.Repository}}:{{.Tag}}	{{.Size}}'
```

---

## The problem I ran into & how I solved it
* **What I was trying to do:** Building the single-stage Dockerfile
* **The error:** `Image size was 1.25 GB and took forever to push and pull.`
* **What actually caused it:** All compilers, header files, and cached apt packages were baked into the final image layers.
* **How I fixed it:** Switched to a multi-stage build: compiled wheels in `builder`, copied only installed packages to `python:3.11-slim`, and cleaned apt caches.
* **Takeaway / lesson learned:** Multi-stage builds let you keep build tools in the build environment and ship only clean runtime binaries.

---

## Key takeaways from today
- The multi-stage build cut image size from 1.25 GB down to 142 MB (an 88% reduction!).
- Put `COPY requirements.txt .` before `COPY . .` so Docker doesn't re-install dependencies when only app code changes.
